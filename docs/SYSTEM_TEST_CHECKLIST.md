# Digital Adaalat system test checklist

The checks use **DigitalAdaalat_Chap_1-3.pdf**, including Tables 3.32–3.77 and its diagrams, and the latest workflow clarifications. The [requirements audit](REQUIREMENTS_VERIFICATION.md) documents how the clarifications change the original use cases. Results in this checklist refer to the current test run. A case is Passed only when its stated assertions were executed successfully. Failed means the observed system behavior contradicted the expectation. Unverified means a step is still unexecuted or blocked, with the reason recorded.

## Test data and method

- Use the isolated PostgreSQL test database and synthetic PDF uploads. Give each role its own browser context and API session. Use separate assigned, unrelated, and other-court accounts where scope matters.
- **Amina v. Hamza** is a Multan civil tenancy case with a tenancy petition, photographs, and a hearing. Amina is the represented litigant, Nadia is filing counsel, Bashir is opposing counsel, Saira is the assigned Reader, and Farooq is the assigned Judge. Use a second civil property case and criminal case for case-type and scope checks.
- Use two registered substitutes, one out-of-chamber lawyer, a pending lawyer, two Process Servers, one independent Reader, an unrelated Judge, a stenographer, and an intern supervised by Nadia. **Notice A** has two recipients, Hamza and Gul. Test one correct Multan address and one incorrect address later corrected by the Reader.
- Examples name the scenario and its required values. The automated suites may use equivalent synthetic fixture names, dates, titles, and amounts. Keep the exact same case, hearing, recipient, request, or revision ID at each handoff.
- Confirm each write from a fresh GET, refresh, or independently signed-in role. For rejected actions, check both the response and that the persistent state did not change. For file checks, distinguish portal preview, direct authenticated download, and independent signature verification.
