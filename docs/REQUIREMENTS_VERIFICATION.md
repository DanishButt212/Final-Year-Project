# Digital Adaalat requirements verification

The checklist covers all 126 pages of DigitalAdaalat_Chap_1-3.pdf. The 46 detailed use cases use the table numbers 3.32–3.77, followed by additional requirements from the chapters, diagram and chat. Tests used isolated sample accounts and the PostgreSQL test database.

## Clarifications applied

- A verified lawyer submits a new case for the represented litigant. The filer remains the lawyer, and the litigant keeps access to their own case and updates. This supersedes litigant self-filing in Tables 3.36 and 3.37.
- The chat calls for an unpaid challan at filing, a fixed amount by case type and a due date visible to the litigant. The document describes a separately generated challan with fee calculations. The requested channels are Bank Transfer, Stripe card, JazzCash and Easypaisa.
- The Reader uses the scheduling board. A last summons disallows coverage even if a request is pending and requires rescheduling. Ordinary coverage is limited to the hearing day and leaves the original lawyer assigned.
- The separate Chamber Portal only receives requests shared by the lawyer. Direct nominees must accept before Reader review. Both paths require Reader and assigned Judge approval.
- Stenographer assignment, Reader provisioning, draft revision, separate judge approval and certificate signing, and release to both assigned lawyers extend the PDF requirements.
- Reader assignment and review of Process Server delivery reports extend the PDF field-execution workflow. A refusal stays recorded as Refused. Reassignments preserve prior attempts and addresses.
- The PDF permits evidence uploads for a party on an existing case. The lawyer-only filing rule covers new case submissions and legal pleadings. Represented litigants retain their ability to add exhibits to their own allocated cases.
- Judge decisions on absence are pending until selected. Only the assigned Reader can enter a PKR amount after the assigned Judge chooses Impose Fine.

## Test runs and open requirements

- All 17 selected Edge workflow tests reached their result. One deliberately asserted the absence of a virtual courtroom link. The Windows runner did not finish teardown, so its console results are the browser evidence.
- The full backend run passed 228 of 230 tests. Reproduced the legacy summons refusal notification and corrected the last-summons browser selector for the automatically opened dialog. All 14 affected tests passed on the targeted retest, including both last-summons browser paths.
- All 46 targeted frontend tests passed after updating outdated fixtures to use a lawyer for pleading uploads. The frontend production build passed.
- Encrypted virtual courtroom launch, joining and moderation are missing from the current build. The existing migration removed the module, and local JaaS application and signing credentials are absent.
- Production payments, external notifications, native hardware or mobile apps, and production signing certificates were outside the available local test environment.

## Reproduce the checks

Use the isolated PostgreSQL test database in `backend/.env.test`. For API checks, run `npm run test:e2e` from `backend`. To include cross-portal checks in the same run, start the development frontend and set `COVERAGE_BROWSER_URL` to its URL. The test harness routes browser requests to its own test API.

For the separate Edge runs, run `npm exec playwright test -- e2e/litigant.spec.ts e2e/field.spec.ts e2e/judge-admin.spec.ts` from `frontend`, with `PW_CHANNEL=msedge`. When another process is using the defaults, set `PW_API_PORT` and `PW_WEB_PORT` to free ports. Run the two suites sequentially because they reset the same test database.
